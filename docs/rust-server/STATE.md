# Rust Server Port — Durable State

> The next cycle reads this FIRST. Plan/acceptance live in [`PLAN.md`](PLAN.md) / [`ACCEPTANCE.md`](ACCEPTANCE.md). This file is the moving state: north star, world model, backlog, cycle log.

## North star  *(confidence: confirmed-by-human — this is the `/goal`)*

Headless Rust server at full feature parity with `bin/Server.exe`, runnable in a Linux container in the cloud, **wire-compatible with the unmodified clients** so a user connects and plays as if the Blitz server were running. No 3D/GUI (the Blitz server's window was GUI-only; logs replace it). Additive under `server-rs/`; no `.bb`/`data/` changes.

### Cycle 57 — 2026-06-16 — LIVE PLAYTEST FIX: dialog-response RACE → options never loaded
- **Symptom:** right-clicking a dialog NPC (merchant) opened the window and showed the text, but the **option buttons never loaded**.
- **Root cause (a real concurrency race in the async-dialog model):** each dialog command runs on the script's own thread as *emit packet → `SetWaiting` → `GetWaitResult`*. The client can reply to the emitted packet **before** the thread has reached `SetWaiting`/`GetWaitResult`. `resume_script` required `r.waiting == true`, so a reply that arrived in that window found no waiting script and was **dropped** — the script then suspended forever waiting for a reply that already came and went. The `async_dialog` unit test missed it because it calls `resume_script` *every* loop iteration (so it always re-delivers once the script is waiting); the live client replies exactly once per packet.
- **Fix:** added `RunningScript::pending_response`. `resume_script` now finds the script by peer (not by `waiting`), delivers immediately if it's parked on `GetWaitResult`, else **buffers** the reply; the next `GetWaitResult` (after the script's `SetWaiting` clears `wait_result`) consumes the buffered response. Handles reply-before-wait and reply-after-suspend.
- **Proof (executed):** new `merchant_dialog_emits_options_with_live_client_responses` — drives Click_Merchant with the **real** client response bytes (`handle_dialog_response`, not the `resume_script("1")` shortcut) and asserts the `N → T → T → O(options)` sequence completes. It reproduced the hang before the fix and passes after. Full suite **161 passing, 0 warnings**.
- **Lesson:** the dialog unit tests used a resume shortcut that masked a genuine race only a real client (one reply per packet, arbitrary timing) exposes — same theme as the prior two playtest fixes. The new test now drives the true client pattern.

#### >>> ASYNC-WAIT MODEL — THE detailed design for the next session (the gateway to dialog/quests/shops) <<<
The Blitz model: scripts are **cooperative coroutines** (BriskVM processes) stepped a bounded number of instructions per server tick; a `WaitResult`-poll loop yields between steps; the engine sets `WaitResult` when the player's response arrives, then the process resumes and the loop exits. Replicate one of:
- **(A) Thread-per-script + channel marshalling (recommended).** Run each hook invocation on its own thread. The `ScriptHost` doesn't touch `ServerState` directly — every `BVM_*` call is sent as `(name, args)` over a channel to the main loop, which executes it against `ServerState` (single-threaded, no locks) and replies with the value + any outgoing packets. A **blocking** command (`GetWaitResult` while a dialog is pending) simply isn't replied to until the player's `P_Dialog` response arrives — the main loop keeps pumping the network meanwhile. State: a `Suspended { peer → (reply_sender, dialog_handle) }` registry; on `P_Dialog` response decode the chosen option and `reply_sender.send(choice)` to resume the thread. Thread joins when the script returns. (`ServerState` need not be `Send`; only the marshalled command/reply values cross the channel.)
- **(B) Re-entrant step machine.** Rewrite the interpreter as an explicit state machine (saved call stack + scope + ip) that returns `Yield(WaitFor)` instead of blocking; the main loop stores the machine and resumes it on the response. More invasive; avoids threads.
The dialog wire encoders + natives are already in place (this cycle); the `P_Dialog` **inbound** response handler (decode the option) + the suspend registry + the chosen model are what remain. Then wire RightClick/Trade hooks (they're dialog-driven), and `DoEvents`/`WaitKill` use the same suspend mechanism.
